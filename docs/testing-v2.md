# DataLocal 2.0 Testing and E2E Strategy

Status: Draft

## Testing layers

```text
Unit tests
    |
Contract tests
    |
Integration tests
    |
End-to-end tests
```

Passing unit tests alone is not a release signal.

## Unit tests

Unit tests cover:

- document validation
- codecs
- field paths
- filters and comparisons
- deterministic sorting
- pagination cursors
- aggregate behavior
- envelope encoding
- exception mapping

Pure core tests must run with `dart test` where possible.

## Contract tests

Every storage adapter runs the same suite:

- open and close
- insert and read
- update and revision checks
- delete
- collection enumeration
- serialized writes
- failed-write behavior
- batch behavior
- reopen persistence where supported
- capability declarations

Every encryption provider runs the same suite:

- round trip
- unique ciphertext for repeated plaintext
- wrong key rejection
- modified nonce rejection
- modified ciphertext rejection
- modified MAC rejection
- associated-data mismatch rejection
- key rotation

## Integration tests

Integration tests use real plugin implementations and platform storage. They
cover:

- SharedPreferencesAsync behavior
- lifecycle initialization
- multiple isolates/engine cache assumptions
- platform key-provider integration
- migration against preference fixtures

## E2E harness

The example application doubles as an automated E2E harness. Test-only commands
are exposed through `integration_test` or a platform-neutral test driver.

Each scenario records a checkpoint, terminates or reloads the application, and
continues from the persisted checkpoint.

## Required E2E scenarios

### Fresh install

1. Clear application storage.
2. Open an encrypted database.
3. Insert nested JSON documents.
4. Verify query and watch results.
5. Restart the application.
6. Verify IDs, metadata, revisions, and data.

### Mutation persistence

1. Insert, patch, replace, and delete documents.
2. Await every operation.
3. Restart the application.
4. Compare the complete committed snapshot.

### Concurrent writes

1. Schedule overlapping inserts, updates, and deletes.
2. Await all operations.
3. Verify commit order and revisions.
4. Restart and verify the same state.

### Interrupted commit

1. Inject a failure after each journal phase.
2. Terminate the application.
3. Reopen the database.
4. Verify rollback or replay according to policy.
5. Verify no uncommitted event was observed.

### Corruption

1. Modify a manifest.
2. Modify an encrypted record.
3. Remove a record referenced by a manifest.
4. Add an orphan record.
5. Verify detection, reporting, and safe repair behavior.

### Encryption

1. Verify stored values do not contain known plaintext.
2. Restart and decrypt using the device-bound key.
3. Rotate the active key.
4. Verify old and new records.
5. Re-encrypt old records.
6. Verify wrong-key and tamper failures.

### Migration from 1.x

1. Install real preference fixtures generated by supported 1.x releases.
2. Open with migration enabled.
3. Interrupt migration and restart.
4. Resume migration.
5. Verify every document and metadata field.
6. Verify legacy values remain until explicit cleanup.

### Upgrade

1. Run the last 1.x application and create data.
2. Install the 2.x application over it without clearing storage.
3. Migrate and verify.
4. Upgrade between prerelease format revisions when applicable.

### Lifecycle

1. Background the application during reads and writes.
2. Resume and verify state.
3. Close and reopen database instances.
4. Verify streams terminate and resources are released.

## Platform matrix

| --- | --- | --- |
| Android | Yes | Primary mobile E2E target |
| iOS | Yes | Keychain and lifecycle coverage |
| Web | Yes | Reload, IndexedDB/local storage, browser automation |

| Linux | Contract + scheduled E2E | Promote to required when CI is stable |

## Failure injection

Storage and encryption adapters expose internal test hooks only through test
libraries. Production public APIs do not expose failure injection.

Failure points include:

- before staging
- after journal prepare
- after record write
- after manifest write
- before commit marker
- after commit marker
- before event emission

## Fixtures

Legacy fixtures are immutable and committed to the repository with:

- producing package version
- producing platform
- plaintext expectation stored separately for tests
- checksum
- generation instructions

Fixtures must contain no real user data or production secret.

## Release gates

Stable release is blocked if:

- any required E2E scenario fails
- a migration fixture cannot be read
- analyzer reports findings
- storage or encryption contract tests fail
- a mutation reports success before durable adapter completion
- corruption is silently converted into empty data
- plaintext or key material appears in default diagnostics
